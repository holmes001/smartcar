# 循迹拟合分析与正交多项式方案

> 对象：`stm32_HAL/smartcar`（STM32H750 + OV2640 188×120 + 双轮差速）
> 本文回答三件事：**工程现在有什么**、**循迹为什么不够好**、**"用正交多项式借内积拟合"到底能解决多少**。
> 所有数字都来自仓库内代码或 `tests/` 的实测输出，可复现（见 §6）。

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 正交多项式 + 内积，可行吗？ | **可行，而且更适合这个场景。** 已在 `Vision_FitPoly()` 实现（三项递推生成离散正交基 + 内积投影），11 个 PC 用例全通过，Cortex-M7 交叉编译 0 告警。 |
| 换了拟合方法，循迹会变好吗？ | **只解决其中一小部分。** 正交基与正规方程是**同一个最小二乘解**（实测系数差 < 1e-4 px），它本身不改变"拟合得好不好"。 |
| 那它的价值在哪？ | 三件事：① 退化场景**知道该降阶**（跨度不足时二次项塌掉），不再靠 `det > 1e-6` 这种有量纲的拍脑袋阈值 —— 实测抖动 6.18 px → **1.05 px**；② 无矩阵求逆、可扩展阶数；③ FLASH +224 B、RAM **−116 B**。 |
| 循迹真正的瓶颈在哪？ | 依次是：**① 前视/航向信息算了却没用**（`slope_ctrl`、`x_look` 在控制器里没有消费者）；**② 转向能力不够**（`yaw_output_ratio=0.5` → 最小转弯半径 180 mm，直角弯转不过去）；**③ 边线配对与数据质量**（`get_max_edge` 配对可疑、压缩循环越界读、`left_lost` 判据太弱）；**④ 模型/坐标**（图像行坐标下的抛物线 ≠ 等曲率道路）。详见 §5。 |

## 1. 工程现状盘点

### 1.1 分层与职责（实际代码，不是设计意图）

| 层 | 目录 | 内容 | 依赖 |
|---|---|---|---|
| L1 硬件驱动 | `HardWare/` | OV2640(DCMI+DMA)、SCCB、电机 PWM、编码器+500 Hz 节拍、LCD、蜂鸣器、串口 | HAL |
| L2 视觉算法 | `camera_process/` | 二值化(Otsu)、扫线、元素识别、**中心线拟合** | 仅 `vision_types.h` |
| L3 控制 | `Control/` | 位置式 PID、底盘（两套档位：占空比 / 串级） | 仅 PID + 编码器/电机 |
| L4 编排 | `Base/app.c`、`app_fsm.c` | 帧处理流水线、按键→事件→状态机、显示 | 全部 |
| L5 服务 | `UI/` | 面板（按键 + LCD）、遥测（JustFloat） | LCD/串口 |

这个分层是**真的干净**：`camera_process` 三个 `.c` 没有 include 任何 `HardWare/` 头文件，`Control/` 不认识图像，`app.c` 是唯一编排者且没有 `extern`。这一点值得保留 —— 它让视觉算法可以整块搬到 PC 上验证（`tests/` 就是这么做的）。

### 1.2 每帧的数据流

```
DCMI+DMA 连续采集 188×120
   │  DCMI_FrameState（唯一同步信号）
   ▼
Vision_OtsuThreshold(行30起 60行, 步长10)   → 阈值夹到 80..120
   ▼
Vision_Binarize(delta)                      → Grayscale[120][188] ∈ {0,255}
   ▼
Vision_ScanLine()                           → lineinfo[120]{left,right,lost,...}
   └─ Vision_FitPath()                      → path_fit{a,b,c,x_ctrl,x_look,slope_ctrl}
   ▼
Vision_ComputePathCenter()                  → path_center[]/path_valid[]（只给绘图）
   ▼
Vision_IsPathValid() ? ──否──► Chassis_Stop()
   │是
   ▼
e_norm = Vision_GetLateralErrorNorm() = (x_ctrl − 94)/94
   ▼
Chassis_UpdateOuter(e_norm, dt)  ── 30 Hz 外环：ω_ref = PID(e_norm) → Δv = ω·L/2 → 左右轮目标
   ▼
Chassis_UpdateInner(2 ms)        ── 500 Hz 内环（TIM6 中断）：编码器实测 → 占空比
   ▼
Vision_DrawEdges() → LCD（每 3 帧刷一次，单次约 8 ms 阻塞）
```

### 1.3 已实现的能力（可直接用的）

- 自动阈值（Otsu，6 位量化直方图）+ 按键微调偏移（PD8/PD9，±120）；
- 逐行连续跟踪的双边线扫描（基准行 + 向上/向下"最近邻沿"延续），带斑马线检测；
- 中心线**加权最小二乘二次拟合**，含两道防御：直线残差门控（固定 25 px）、曲率钳位（|c| ≤ 60）；
- 控制行外推：第 60 行丢线时仍能输出偏差（实测 50~70 行全丢，误差 0.05 px）；
- 两套底盘控制档位（占空比 / 真物理量纲串级），500 Hz 速度环；
- 状态机（ADJUST/RUN）、LCD 面板、VOFA+ 遥测、按键现场调参（阈值 / 右轮补偿）；
- PC 端可跑的算法测试（`tests/test_path_fit.c`，11 个用例）。

### 1.4 一眼可见的空缺

| 位置 | 现状 |

## 2. 循迹链路分析：误差到底从哪来

把"车跑不好"拆成四个独立来源，才能判断换拟合方法有没有用。

### 2.1 测量层：边线本身可能是错的

这一层的问题**比拟合大**，且都在 `scan_line.c` 的扫线部分：

1. **基准行的右边线配对可疑**（`get_max_edge`，:166-167）
   ```c
   lineinfo->left  = edge_store[max_idx];
   lineinfo->right = edge_store[lineinfo->edge_count - 1];  // 取"最后一个沿"
   ```
   `right` 取的不是 `max_idx + 1`（配对的右沿），而是全行最后一个跳变沿。只要最后一段是噪声/远处干扰，基准行的 `right` 就错，而**整条向上搜索链都以它为参考**（`get_best_edge` 用上一行结果做最近邻），错误会逐行传染。

2. **压缩循环越界读 + 未初始化标志**（:239-263）
   ```c
   uint8_t dst_flag;                              // 未初始化就参与 if (dst_flag == 1)
   edge_store[dst] = edge_store[i + 2];            // i+2 可能 >= edge_count（读到上一行残留沿）
   lineinfo->edge_count -= 2;                      // 边缩容边用旧上界循环
   ```
   这条分支的触发条件是 `8 × 黑块占比 > 主区间宽度`（赛道中有杂物/斑马线/十字），偏偏是直角弯、路口最容易命中的场景。读进来的"幽灵沿"会直接变成错误的左右边界。

3. **"丢线"判据太弱**（:290-305）
   `left_lost` 只在 `left ≤ 0` 时置 1，`right_lost` 只在 `right ≥ 187` 时置 1。也就是说：边线跑到画面中间（典型的误检）依然算"有效行"，会以 `(left+right)/2` 的形式混进拟合。真正挡住它们的只有 §2.2 的 25 px 门控。

4. **`lineinfo[y].y` 少赋值**（`Vision_ScanLine` :44-49）
   `line_single()` 和向下搜线循环都没有写 `y`，靠 `memset` 的 0 顶着。于是行 0~5 的 `y` 永远是 0，`get_best_edge` 里 `lineinfo->y > 20` 恒假 → **行 0~5 一律标成 `whole_lost`**。当前恰好被 `VISION_BASE_LINE = 5` 掩盖（拟合从第 5 行起，而第 5 行因 `y=0` 被判丢线），代价只是少了第 5 行；但只要有人把 `BASE_LINE` 调小，近场会**整片静默失效**。

### 2.2 拟合层：本次改动的部分

现状：`x(t) = a + b·t + c·t²`，`t = (row − 60)/60 ∈ [−1, 1]`，权重 `w = 1/(1+0.6|t|)`，直线残差 > 25 px 的行剔除，`|c|` 夹 60。

三个**方法层面**的已知极限（`docs/API_MANUAL.md` §12.2 已经诚实记录）：

- **门控把可表达曲率钉死在 c ≈ 37**：抛物线与直线最大差 ≈ 2c/3，超过 25 px 的合法弯行会被当成坏行剔掉 → 曲率偏保守，预瞄不足。
- **"强弯 + 中等坏块"不可分**：强弯本身相对直线的偏差已到 19 px，而 40 px 坏块残差 21~25 px，两者重叠，任何全局阈值都分不开。
- **门控是硬阈值**：`w` 只有 0/1 两态，坏行是"整行丢弃"，没有按残差大小渐减，信息损失大。

### 2.3 控制层：**真正的大头**

- **当前工作区的差速项是共模的**（`chassis.c:Chassis_UpdateOuter`）：左右轮都写 `base + Δv`，
  见 §5 开头那个框 —— 这已经不只是"效果不好"，而是**没有转向**。先修这个，再谈其它。
- **只有横向偏差，没有航向/前视**：`e_norm` 一个标量进 PID，`slope_ctrl`（航向）和 `x_look`（预瞄）虽有值却无人使用。这是典型的 "preview P 控制"：预瞄点越远等效增益越大，而没有任何阻尼项，30 Hz 采样下很容易在弯里来回摆。
- **转向能力不足**：`yaw_output_ratio = 0.5`、`L/2 = 90 mm` ⇒ `R_min = (L/2)/ratio = 180 mm`。90° 直角弯的半径约 100 mm，**几何上就转不过去**，与拟合精度无关。
- **积分项易被丢线反复清零**：`Vision_IsPathValid() == 0` 时直接 `Chassis_Stop()`（duty = 0 + 清积分），一帧丢线就硬停，重新找到线时从零起速。

### 2.4 时序层

- 外环 = 帧率（约 30 Hz），而 LCD 刷屏一次约 8 ms，**每 3 帧就有一次 8 ms 的阻塞插在控制周期里**（`APP_IMAGE_DISPLAY_DIV = 3`）。`dt` 抖动会直接进 PID 的积分/微分。
- `DCMI_FrameState = 0` 在**消费之前**清，DMA 仍在写下一帧，图像存在撕裂可能；没有"帧完成→处理副本"的双缓冲。

> 小结：**拟合精度不是主因**。即使把 a/b/c 算到 0.001 px，只要 `yaw_output_ratio=0.5`，90° 弯依旧过不去；只要航向不进控制器，摆头依旧存在。这决定了本次改动的定位：把拟合做"对且稳"，并把改进空间按性价比排序交给上层决策。

## 3. 正交多项式方案

### 3.1 数学

目标函数没变：

```
min Σ wᵢ·(xᵢ − p(tᵢ))² ,   p(t) = a + b·t + c·t²
```

**直接法**（原实现）对幂基 `{1, t, t²}` 解正规方程 `G·[a b c]ᵀ = r`，其中 `G_jk = Σ w·t^(j+k)` 是 Hankel 矩阵。问题不在 `κ`（`t` 归一化后满幅 `κ ≈ 5.8`，很好），而在**退化时没有判据**：

- 有效行只剩远端 1/3 幅时 `κ ≈ 1e4`，`float32` 有效位数被吃掉；
- `det` 会随跨度变窄**连续趋近 0 而永不为 0**，于是"多小算奇异"只能拍一个**有量纲**的绝对阈值（原代码 `1e-6`）。实测该阈值几乎只在真正精确奇异时才触发，因此**降阶这件事从来没发生过** —— 该退的时候不退，硬解出一个由噪声主导的二次项。

**正交法**：对加权离散内积 `⟨f,g⟩ = Σ wᵢ·f(tᵢ)·g(tᵢ)`，用三项递推（Stieltjes 正交化）造基：

```
p₀ = 1
p₁ = (t − α₁)·p₀                 α₁ = ⟨t·p₀,p₀⟩/⟨p₀,p₀⟩
p₂ = (t − α₂)·p₁ − β₂·p₀         α₂ = ⟨t·p₁,p₁⟩/⟨p₁,p₁⟩
                                 β₂ = ⟨p₁,p₁⟩/⟨p₀,p₀⟩
```

它们满足 `⟨pⱼ,pₖ⟩ = 0 (j≠k)`，正规方程因此**对角化**，系数就是投影：

```
cₖ = ⟨x,pₖ⟩ / ⟨pₖ,pₖ⟩
```

没有矩阵、没有 Cramer 展开、没有 `det`，只有内积和一次除法。算完换回幂基（对外接口不变）：

```
c = c₂
b = c₁ − c₂·(α₁+α₂)
a = c₀ − c₁·α₁ + c₂·(α₁·α₂ − β₂)
```

> 这正是"行数有限"时该用的东西：离散正交多项式本来就是为**有限节点集**定义的（等距 + 等权时退化为经典 Chebyshev；这里节点不等距、还带权重，所以用递推现场生成，而不是查表）。也正因为递推只依赖节点本身，**每帧有效行变化不需要任何预处理**。

### 3.2 它到底改变了什么（诚实的边界）

| 说法 | 是否成立 |
|---|---|
| 换成正交基后拟合**更准**（对同一批数据） | ✘ 不成立。最小二乘解唯一，两者是**同一个点**（实测系数差 < 1e-4 px，见 §4 用例 9）。 |
| 能修复"强弯 + 中等坏块"的掩蔽 | ✘ 不能。那是**数据不可分**的问题，与服务基无关。 |
| 退化/窄跨度时更稳 | ✔ **成立，且可量化**：`⟨p₂,p₂⟩` 是相对判据，跨度不足时精确塌向 0，据此降阶（抖动 6.18 → 1.05 px）。 |
| 不再需要 `det` 的魔法阈值 | ✔ 成立。判据是 `<pₖ,pₖ>/<p₀,p₀>`，无量纲、与 t 的平移无关。 |
| 数值条件更好 | ✔ 成立（G 对角化、条件数归一到 1），但**在满幅满行的正常帧上这点收益看不出来**。 |
| 更省/更好扩展 | ✔ 成立：无 3×3 求解；要上三次/四次只需多跑一趟递推（`order+1` 趟）。 |

一个必须说清的细节：秩判据是**相对**的，但门限值仍与 `t` 的归一化绑定。当前 `t ∈ [−1,1]`、门限 `1e-3`，等价于"**有效行跨度 < 约 40 行（1/3 幅）就降为直线**"（标定表见 `vision_types.h` 的 `VISION_FIT_ORTHO_MIN_REL`）。若改动归一化尺度，门限要同步换算。

### 3.3 实现落点

| 文件 | 改动 |
|---|---|
| `camera_process/Inc/vision_types.h` | 新增 `VISION_FIT_ORTHO_MIN_REL`、`struct path_poly_s`；`path_fit_s` 增加 `resid_rms` / `t_span` / `order`；删掉一段过时注释 |
| `camera_process/Inc/scan_line.h` | 新增 `Vision_FitPoly()` 声明 + 对照表；更新 `Vision_FitPath()` 文档 |
| `camera_process/Src/scan_line.c` | 删 `Fit_SolveOnce()`/`Fit_SolveLineOnce()`（两者共 135 行）；新增 `Vision_FitPoly()`（纯数学、无全局状态）与 `Fit_ResetInvalid()`；`Vision_FitPath()` 改为"压缩样本 → 直线 → 25 px 门控 → 二次（可降阶）→ 曲率钳位 → 填结果" |

## 4. 实测数据

环境：`gcc 16.1`(x86_64) / `arm-none-eabi-gcc 13.3`，`-std=gnu11 -Wall -Wextra`，0 告警。`tests/test_path_fit.c` 全部用例 **ALL PASS（11/11）**。

### 4.1 与旧实现的等价性（用例 9，满幅 110 行，±0.5 px 噪声）

| 系数 | 正交投影 | 正规方程 | 差 |
|---|---|---|---|
| a | 93.9828 | 93.9829 | 0.0001 |
| b | −18.0468 | −18.0469 | 0.0001 |
| c | 34.1341 | 34.1338 | 0.0003 |

结论：**同一个估计量**。想靠换基函数提升精度是行不通的。

### 4.2 窄跨度（用例 10）：直道 + 只剩行 0~30 + ±2 px 噪声，200 次蒙特卡洛

真值 `x = 94 − 10t`，控制行处应为 94。

| 方法 | `x_ctrl` 标准差 | 最大偏差 | 降阶次数 |
|---|---|---|---|
| 正交基（本次） | **1.05 px** | **2.90 px** | 200/200（全部降为直线） |
| 正规方程（原） | 6.18 px | 15.43 px | 0（无从判断） |

偏差均值两者都≈0，**差别在抖动**：原实现每帧硬解一个由噪声主导的二次项，外面再靠 `|c| ≤ 60` 的钳位兜底；新实现直接判定"这段数据撑不起二次项"，用直线。抖动降低约 **5.9 倍**。

### 4.3 退化（用例 11）：只有 2 个不同行号各重复 4 次

| 方法 | order | c | a（应 94） |
|---|---|---|---|
| 正交基 | 1（自动降阶） | 0.0000 | **94.0000** |
| 正规方程 | — | **−91.4286** | **105.1429** |

`det` 因浮点累加变成一个非零小数（大于旧阈值 `1e-6`），旧代码于是照除不误，二次项被放大到荒谬值。这类帧在直角弯"只剩两条固定行能扫到"时并不罕见 —— 而它恰好是 `§12.2` 里记录过的"曲率非常大的抛物线"现象的一个来源。

### 4.4 资源

| 项 | 旧 | 新 |
|---|---|---|
| `scan_line.o` .text | 2304 B | **2528 B**（+224 B） |
| `scan_line.o` .bss | 8796 B | **8680 B**（−116 B） |
| 其中拟合相关 | `Vision_FitPath` 1104 B | `Vision_FitPath` 616 B + `Vision_FitPoly` 712 B |

RAM 变小是因为采样缓存从"按行三个数组（119 个元素）+ 残差数组"改成"按有效行压缩的三个数组"。

## 5. 提升空间（按性价比排序）

> 只列**能指出具体代码位置**的项；"预期收益"是工程判断，不是实测。

### P0 — 把已经算好的信息接进控制器（改动最小、收益最大）

| 项 | 位置 | 做法 | 预期 |
|---|---|---|---|
| **差速符号 bug** | `chassis.c:Chassis_UpdateOuter`（当前工作区状态） | 见下方"必须先确认的一件事" | **当前外环没有任何转向能力** |
| 航向进环 | `app.c:App_HandleFrame` → `Chassis_UpdateOuter` | 外环输入从单标量改为 `e_ctrl` 与 `slope_ctrl` 的组合（如 `e = e_ctrl + k_θ·slope_ctrl`），或直接用前视偏差 | 给 preview-P 补上阻尼，抑制弯中摆动 |
| 前视可选 | `Element_recognition.c` 已有 `Vision_GetLateralErrorLookaheadNorm()` | 直接替换/加权混合，同时按注释下调 `yaw_kp` | 提前转向，减少"进弯晚、出弯冲" |
| 可信度门 | 新增 `path_fit.resid_rms` / `t_span` / `order` | `resid_rms` 大或 `order==1` 时降低增益/维持上次输出 | 坏帧不再直接触发 `Chassis_Stop()` 硬停 |

> **必须先确认的一件事（比拟合重要得多）**
> 差速运动学只有两个式子：`v = (v_R + v_L)/2` 决定走多快，`ω = (v_R − v_L)/b` 决定转多快。
> 所以"差速转向"= 给两个目标速度加**一正一负**的一对 `Δv`；同一个 `Δv` 加到两边，
> 差值不变、`ω` 不变，只是整车加速。
>
> 当前工作区的 `Control/Src/chassis.c` 里 `Chassis_UpdateOuter()` 是：
> ```c
> s_wheel_target[MOTOR_L] = s_cfg.base_speed_mm_s + delta_v;
> s_wheel_target[MOTOR_R] = s_cfg.base_speed_mm_s - s_cfg.right_comp_mm_s + delta_v;
> ```
> 两式相减得 `target_L − target_R ≡ right_comp`（当前配置为 0）——**与外环输出 `e_norm` 完全无关**。
> 这不是差速，是共模增速。下层也不会把它变回来：`Motor_SetDuty()` 正占空比即正转、左右无软件镜像；
> `encoder.c` 里两侧 DIR 极性相反只是把编码器**归一化成"正值 = 前进"**，内环看到的符号是一致的。
>
> **30 秒验证（不用改代码）**：
> 1. VOFA+ 看那两条**目标速度**曲线（通道 1 = 目标 R、通道 3 = 目标 L）——转弯时应一条涨一条落，
>    当前是**同涨同落、差值恒定**；
> 2. 或架空车轮、人为制造大的 `e_norm`，看哪一侧转得快，两侧一样快即无差速。
>
> 修法（保持一正一负，只改右轮 Δv 的符号）：
> ```c
> s_wheel_target[MOTOR_L] = s_cfg.base_speed_mm_s + delta_v;
> s_wheel_target[MOTOR_R] = s_cfg.base_speed_mm_s + s_cfg.right_comp_mm_s - delta_v;
> ```
> 若实测转向相反，则整体取反（`L = base − Δv; R = base + comp + Δv`），但**绝不能两边同号**。
> 方向由 `e_norm` 的符号约定（图像列方向）与电机接线共同决定，必须上车验一次。
> 注意 `git HEAD` 里的版本恰好是"一正一负"（`L = base − Δv, R = base + comp + Δv`），
> 是一对真正的差速，只是方向与它自己的注释相反 —— 那次改动本意是修方向，结果把差速改没了。
> 未使用的 `Chassis_Update()`（占空比档）同样是"一正一负"，可作对照。

### P1 — 转向能力（几何问题，必须改参数）

`yaw_output_ratio: 0.5 → 0.9`（`CHASSIS_CASCADE_CONFIG`）：`R_min = (L/2)/ratio` 由 180 mm 降到 **100 mm**，90° 弯才谈得上过。代价：内侧轮可能接近堵转，差速功耗上升；建议同时把 `base_speed` 降到 300~400 mm/s 试。

丢线时从"硬停 + 清积分"改成"保持上次差速 N 帧 + 积分冻结"，可显著减少弯里的反复刹停/窜车。

### P2 — 扫线数据质量（收益大，但要动扫描算法）

1. `get_max_edge` 的 `right` 改为 `edge_store[max_idx + 1]`（原注释自己都在怀疑这一行）；
2. 压缩循环修 `dst_flag` 初始化与 `i + 2` 越界，且先在副本上操作完再更新 `edge_count`；
3. **宽度一致性检查**（新增，成本极低）：`right − left` 与中位数偏差 >20% 的行直接判无效。误配对几乎必然伴随宽度突变，这比事后 25 px 门控更早、更准；
4. `left_lost/right_lost` 的判据从"贴边"扩展为"跳变沿在中部/宽度不合理"；
5. `lineinfo[y].y` 在 `line_single()` 与向下循环里补上赋值（1 行修复）。

### P3 — 模型与坐标（收益中等，改动较大）

二次多项式在**图像行坐标**下只是对道路的局部近似：等曲率道路在透视下并非 `row` 的抛物线。可选路线：

- 逆透视（bird's-eye）后在 `(X, Y)` 平面拟合圆弧/三次曲线，再投回图像；或
- 直接拟合曲率 `1/R` 与 `x_ctrl` 两个物理量（与 §5 P0 的航向控制天然配套）；或
- 把阶数升到 3（正交基下只是多一趟递推，`order` 参数已支持），用 `t_span` 与 `rms` 决定是否值得保留。

### P4 — 鲁棒回归替代硬门控

把 25 px 硬阈值换成 IRLS（Huber / Tukey，σ 用 MAD 估），权重连续衰减而不是整行丢弃。这样"强弯 + 中等坏块"虽仍不可分，但**不会因为门控把合法弯行整片剔掉**，可表达的曲率不再被钉死在 c≈37。注意：这会改变 §12.2 的实测结论，需要重新扫参数（`tests/` 里已有可控的离群点/坏块用例，可直接复用）。

### P5 — 时序与稳定性

- LCD 刷屏节流已存在，但 8 ms 阻塞仍落在控制周期里；跑车时把 `APP_IMAGE_DISPLAY_DIV` 调大（或运行态关图像刷新）；
- `DCMI_FrameState` 改在**处理完之后**清，或做"帧完成→拷副本→处理副本"的双缓冲，消除撕裂；
- 外环 `dt` 用固定周期（例如按帧号/定时器）而不是 `HAL_GetTick()` 差值，避免 LCD/串口阻塞污染 PID。
